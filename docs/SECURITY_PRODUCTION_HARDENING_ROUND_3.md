# Security Production Hardening — Round 3

## Login throttling architecture

- Redis is not a repository dependency or configured service. Production login throttling uses the existing MySQL/InnoDB `rate_limits` table created by migration `0001_core_security_and_sessions`; no new dependency or migration is required.
- Four login surfaces use a shared, transactionally locked fixed-window store in MySQL: Admin, Customer, Vendor and Reseller. Keys contain only a SHA-256 hash of the source IP and, for the second budget, a normalized-and-hashed account identifier. Session IDs are intentionally not used, so session rotation does not reset a budget. Account phone normalization preserves the existing Bangladesh `+880`/`880`/`0` aliases.
- Each portal has two budgets: a generous IP budget (currently 2,000/15 minutes) and a tighter source-IP + account budget (Admin 12, Customer 10, Vendor 8, Reseller 8 per 15 minutes). No account-only hard-denial budget remains: attempts from other IPs cannot exhaust a victim's account-wide quota. These are initial code policy values and remain adjustable via the portal `createLoginRateLimiters` options; operators should review them against observed traffic/CGNAT before changing them.
- The pair bucket returns `req.loginThrottle` metadata including a `challengeSuggested` hint near the threshold. No CAPTCHA, SMS, email, device fingerprint, or other provider is configured or implied; session IDs are deliberately not used as an independent throttle key because they are attacker-rotatable. A future owner-approved step-up/recovery handler can use this extension point. A request over a pair/IP bucket receives HTTP 429 with `Retry-After`; using a different network can recover from a source-IP/account bucket, while expiry resets it automatically. This still permits a same-source-IP/account lockout until expiry; the broader account-wide 100-attempt denial risk is removed, but this narrower residual requires operations monitoring and owner review of the per-portal thresholds.
- MySQL operations use `UTC_TIMESTAMP()`, an InnoDB transaction and `SELECT ... FOR UPDATE` around the row mutation. Requests that hit an already-full bucket are not allowed; attempts beyond the cap do not keep increasing its count. Expired rows are opportunistically deleted in bounded batches (up to 500 every 256 bucket operations) using the existing `reset_at` index. Only expired entries are removed, including expired OTP/security bucket entries that share this table.
- When `DB_CLIENT=mysql`, an unavailable or failing rate-limit store fails closed with a generic HTTP 503; it does not silently switch to per-process counters. In development/test with `DB_CLIENT=sqlite`, an explicitly local process-memory adapter is used; it is not distributed or suitable for production. No account/password data is sent to the limiter store.
- Deployment prerequisite: apply the existing migration history so `rate_limits` exists and the application DB principal can `SELECT`, `INSERT`, `UPDATE` and perform bounded `DELETE` on that table. Do not add/renumber migrations for this change. The repository currently contains a separate duplicate migration version `0028`; this work does not suppress or resolve it.

## CSP and response headers

- `server.js` now emits `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, a restrictive `Permissions-Policy`, and a `Content-Security-Policy-Report-Only` policy. Production responses additionally receive `Strict-Transport-Security: max-age=31536000` and `X-Frame-Options: SAMEORIGIN`; HSTS is omitted outside production and X-Frame-Options remains omitted in non-production to retain Arena preview embedding.
- The report-only policy does not break current pages and contains no `unsafe-inline` or `unsafe-eval`. It permits the observed same-origin assets plus jQuery (code.jquery.com), Bootstrap/Feather (jsDelivr), Toastr/Font Awesome (cdnjs), and Google Fonts. Product images may use HTTPS/data/blob sources; connections remain same-origin. Report submissions are accepted at `/api/security/csp-report`, limited to 60 per minute per IP, and server logs retain only directive/disposition and origins (not full document/blocked URLs or query strings).
- Audit of the checked-in EJS pages found about 66 inline `<script>` tags, 5 `<style>` blocks, and 49 inline event-handler occurrences. Therefore an enforcing CSP or a nonce-only policy is not enabled yet: existing inline code would be blocked, and doing so blindly could break portals, storefront and payment-related UI. The report-only policy is a measurement/transition step. Review violation reports, migrate inline handlers/styles/scripts to external assets or per-response nonces/hashes, test all flows including third-party payment UX, then separately approve enforcement. Report-only is not a substitute for an enforcement rollout or a browser monitoring/alerting process.
- No `frame-src` payment provider was identified in the inspected templates. If a provider later uses hosted frames, add its exact approved origin only after confirming the integration. `Permissions-Policy` disables camera, microphone and geolocation; revisit only if an approved product feature needs them.

## Verification and remaining scope

- Automated unit tests cover login identifier normalization, shared-store injection behavior, per-IP/account isolation, avoidance of account-wide lockout, expiry, fail-closed 503 handling, and production/non-production security header differences.
- Database-backed MySQL 8.0 and MariaDB 10.11 concurrency/restart tests require a disposable local test database with the existing core migration applied. Do not run these against production or customer data. They remain unverified when no such DB is provisioned; a passing in-memory test is not evidence of MySQL behavior.
- Existing duplicate `0028` migration collision is not hidden or changed here. Courier-owned files and migration `0029` are out of scope.
