# PHASE 06 — PRODUCTS, INVENTORY, PURCHASES & SUPPLIERS

**Status:** `IN PROGRESS` — the tested vertical slice below is implemented; full Phase 06 acceptance is not yet met.

## Implemented vertical slice

- `src/repositories/phase06Repository.js` provides product creation and catalog metadata editing (excluding identifiers/inventory), bounded variant create/edit/soft-deactivation (excluding SKU and inventory mutation), supplier create plus profile/active-status edit with transactional audit, warehouse/vendor stock listing, reason-required inventory adjustment, product archive/restore, multi-line draft PO creation, partial/full purchase receipt, and bounded list queries.
- `src/routes/phase06.js` mounts the feature at `/admin/phase06`, requires an admin session and per-write CSRF token, validates through the repository, serves an inventory JSON endpoint, and provides dependent bilingual category → subcategory → child-category selectors on product creation/edit; server-side validation rejects inactive, missing, malformed, or unrelated descendants and the edit query/form preserves valid stored descendant IDs plus nested variant create/update, product-gallery reorder, and supplier-profile lifecycle actions. New routes use the canonical repository, not the synchronous SQLite facade in MySQL mode.
- `views/admin/phase06.ejs` reuses the existing Admin shell and shared locale/formatters; both `bn` and `en` UI dictionaries have matching Phase 06 keys.
- `0004` adds product type; supplier code/contact/email/business identifier/notes; PO totals, charges and cancellation reason; purchase-line variant/return metadata; unit-cost detail to the stock ledger; and uniquely identified purchase receipts with request hashes.
- A new product's optional opening stock is recorded once in `stock_ledger`. Product creation without an explicit opening quantity starts at zero. Product archive disables storefront status and preserves relational history; no product hard delete is offered in this module. Catalog create/edit validates active category/subcategory/child-category relationships and active brand references, slug uniqueness and integer-paisa pricing, and audit before/after state in the same transaction. They deliberately leave SKU/barcode, parent stock/reservations, stock ledger, variant rows/prices, archive/status and approval unchanged.
- Variant management uses the existing `product_variants` model without a schema migration: administrators can create a variant with zero stock and update its size/color labels, integer-paisa price override and active state. The existing globally unique `variant_sku` index arbitrates concurrent duplicates; SKU is immutable after create. The schema has no variant barcode field. A zero price preserves the existing checkout rule that falls back to the product sale/regular price. Updates never alter variant stock/reserved quantities or ledger rows; deactivation is soft and leaves cart, order, reservation and ledger foreign-key references intact. No variant hard-delete or stock-adjustment route was introduced. Before/after audit events share the MySQL/SQLite transaction. The Admin form supports Bangla/English labels.
- Manual adjustment requires a reason, uses a MySQL `SELECT ... FOR UPDATE` transaction on the product, prohibits negative stock, and writes the stock change, ledger movement, and `inventory.adjust` audit event in the same transaction. The SQLite compatibility adapter likewise writes its audit event inside its existing adjustment transaction. Unknown stock-pool values are rejected. A vendor-pool adjustment requires the product be assigned to a vendor.

## Gallery upload and assignment (MySQL/MariaDB CI verified)

- The product edit gallery section now accepts up to six JPEG, PNG, WebP or GIF uploads using the existing persistent `UPLOAD_DIR/custom` storage contract and randomized filenames. - The upload route remains behind the existing admin authentication and `inventory.manage` RBAC checks. - Filesystem writes cannot participate in the SQL transaction: a process crash between upload and assignment can leave an unassigned file. No orphan sweeper is added because ownership of older files cannot be proven. Ordinary request failures use best-effort cleanup; do not claim filesystem/database distributed atomicity.

### Variant receiving inspection

The table structure can associate a purchase item with `product_variants.id`, but that field is not wired into purchase creation or receipt processing in either adapter. Current receipt logic is consistently product-level and also applies existing product cost handling. A variant-specific workflow would change the target balance and could affect cost treatment; the legacy `variant_id` column alone is not an approval for those behaviors. Keep variant receiving blocked until the owner confirms whether a PO line may target a variant, the stock pool/balance to change, how parent-product totals remain separate, and whether disabled variants can be received. This does not require inventing batch/lot/expiry behavior; any such tracking remains a separate owner decision.
