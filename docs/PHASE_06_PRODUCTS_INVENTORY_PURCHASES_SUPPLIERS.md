# PHASE 06 — PRODUCTS, INVENTORY, PURCHASES & SUPPLIERS

**Status:** `IN PROGRESS` — the tested vertical slice below is implemented; full Phase 06 acceptance is not yet met.
**Scope:** `P06-01`–`P06-05` only. No Phase 07+ work is represented as complete.
**Database:** MySQL/InnoDB is the production boundary; local SQLite is retained as a non-production compatibility/test adapter.
**Migration:** `0004_phase06_inventory_purchases_suppliers` (`.up.sql` / `.down.sql`), reversible additive DDL.

## Implemented vertical slice

- `src/repositories/phase06Repository.js` provides product creation and catalog metadata editing (excluding identifiers/inventory), bounded variant create/edit/soft-deactivation (excluding SKU and inventory mutation), active supplier creation with transactionally coupled `supplier.create` audit, warehouse/vendor stock listing, reason-required inventory adjustment, product archive/restore, multi-line draft PO creation, partial/full purchase receipt, and bounded list queries.
- `src/routes/phase06.js` mounts the feature at `/admin/phase06`, requires an admin session and per-write CSRF token, validates through the repository, serves an inventory JSON endpoint, and provides active bilingual category/brand selectors on product creation/edit plus nested variant create/update and product-gallery reorder actions. New routes use the canonical repository, not the synchronous SQLite facade in MySQL mode.
- `views/admin/phase06.ejs` reuses the existing Admin shell and shared locale/formatters; both `bn` and `en` UI dictionaries have matching Phase 06 keys.
- `0004` adds product type; supplier code/contact/email/business identifier/notes; PO totals, charges and cancellation reason; purchase-line variant/return metadata; unit-cost detail to the stock ledger; and uniquely identified purchase receipts with request hashes.
- A new product's optional opening stock is recorded once in `stock_ledger`. Product creation without an explicit opening quantity starts at zero. Product archive disables storefront status and preserves relational history; no product hard delete is offered in this module. Catalog updates validate active category/brand references, slug uniqueness and integer-paisa pricing, and audit before/after state in the same transaction. They deliberately leave SKU/barcode, parent stock/reservations, stock ledger, variant rows/prices, archive/status and approval unchanged.
- Variant management uses the existing `product_variants` model without a schema migration: administrators can create a variant with zero stock and update its size/color labels, integer-paisa price override and active state. The existing globally unique `variant_sku` index arbitrates concurrent duplicates; SKU is immutable after create. The schema has no variant barcode field. A zero price preserves the existing checkout rule that falls back to the product sale/regular price. Updates never alter variant stock/reserved quantities or ledger rows; deactivation is soft and leaves cart, order, reservation and ledger foreign-key references intact. No variant hard-delete or stock-adjustment route was introduced. Before/after audit events share the MySQL/SQLite transaction. The Admin form supports Bangla/English labels.
- Manual adjustment requires a reason, uses a MySQL `SELECT ... FOR UPDATE` transaction on the product, prohibits negative stock, and writes the stock change, ledger movement, and `inventory.adjust` audit event in the same transaction. The SQLite compatibility adapter likewise writes its audit event inside its existing adjustment transaction. Unknown stock-pool values are rejected. A vendor-pool adjustment requires the product be assigned to a vendor.
- Authenticated MySQL HTTP acceptance coverage in `tests/phase09-dashboard-mysql.test.js` covers inventory-adjustment authentication, `inventory.manage` denial, CSRF, valid movement, invalid quantity, missing product, persisted ledger/audit details, and failure rollback. Supplier-create HTTP coverage checks authentication, permission denial, CSRF, field validation, persisted supplier/audit values, and rollback on audit-insert failure. Exact-SHA MySQL 8.0 CI run [`40493990393`](https://github.com/mrtumi2026/Mrtumi/actions/runs/40493990393) passed on `e1f6a2a2876cffc173eaba0c623099ed38071359`.
- Purchase creation validates and calculates line totals server-side in integer paisa, validates supplier and product records, and creates a `draft` PO without increasing stock. Receipt updates are transactional, row-locked, partial-receipt aware, request-hash/idempotency checked, and update stock and ledger together.
- Inventory valuation is not presented as a financial report. `cost_price_paisa` is maintained using a moving weighted-average cost on receipts; vendor consignment stock and retail-margin valuation are excluded. This calculation still requires additional audited purchase-return/write-off policies before being used for management reporting.
- Image-upload middleware denies SVG and other active-content formats, limits size and count, uses random names, checks raster magic bytes, and respects configured `UPLOAD_DIR/custom` storage. The bounded gallery UI at `/admin/phase06/products/:id/edit#gallery` reorders only the product's complete current list of existing safe raster paths under `/uploads/product/` or `/uploads/custom/`; the first path becomes `image_url`, and the ordered list is written to the existing MySQL `gallery_json` / SQLite `gallery` field. The repository checks real files under their approved roots, symlink/path containment, allowed raster extensions/signatures, product-local membership, complete-list uniqueness, admin permission and CSRF, and couples before/after audit with both product fields in one transaction. Unsafe/missing legacy references fail closed and are not rendered; no upload, list removal, file deletion, or addition of unassigned/custom paths is provided because there is no product-media ownership table. Shared files remain untouched.

## Bounded product CSV update/export (implementation awaiting exact-SHA MySQL CI)

- `src/utils/productCsv.js`, `src/repositories/phase06ProductCsvRepository.js`, and `/admin/phase06/products/import/{preview,commit}` plus `/admin/phase06/products/export.csv` implement update-only catalog import keyed by SKU. The fixed export/import contract contains only existing editable product fields; barcode is an immutable identity check, not a lookup key or update. No create/delete operation is offered.
- Preview parses and validates every row, bounds bytes/row count, normalizes through the existing product edit validator, requires active taxonomy references, rejects duplicate CSV SKU/barcode/slug values and ambiguous database SKU/barcode resolution, and reports row-indexed actionable errors. Mixed valid/invalid files are all-or-nothing: no row is committed if any row is invalid. Preview is read-only. A short-lived session-bound preview token and CSV digest bind the separate authenticated, `inventory.manage`, CSRF-protected commit to the exact previewed file; commit reparses/revalidates and applies updates plus minimized audit records in one transaction. Concurrent changes are checked under row locks.
- Explicit exclusions: stock and reservations, variants, approval/archive/status, financial/ledger data, and media are neither import columns nor mutated by the workflow. Export excludes those same sensitive/stateful fields and uses CSV quoting plus formula-leading cell neutralization. Export audit records only row count/format, not cell values. No bulk delete exists.
- SQLite-adapter tests currently pass mixed-row blocking, read-only preview, explicit commit, excluded-field preservation, rollback, identifier ambiguity/duplicates, quoting, and formula safety. MySQL HTTP coverage is authored for export/preview/commit, persisted results, auth/permission/CSRF, invalid/stale/duplicate/ambiguous rows, rollback and preservation; it is **skipped locally** without MySQL. Do not claim MySQL/MariaDB compatibility until both MySQL 8.0 and MariaDB 10.11 jobs pass on the exact final SHA.
