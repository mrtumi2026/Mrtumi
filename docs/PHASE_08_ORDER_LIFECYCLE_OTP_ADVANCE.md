# PHASE 08 — ORDER MANAGEMENT, INCOMPLETE ORDERS, OTP & ADVANCE PAYMENT

**Status:** `IN PROGRESS` — order/refund lifecycle primitives, a guarded admin UI, consent-only recovery records, OTP/advance configuration utilities, and an inventory reservation foundation are implemented. Live MySQL 8.0 evidence is pending.
**Database:** Phase 08 repository routes require MySQL/InnoDB. This work did not convert the existing SQLite-backed checkout or connect it to these functions. Production must remain MySQL-only.
**Migration:** `0006_phase08_order_lifecycle` is additive and reversible. It adds nullable refund idempotency/provider-reference columns, order-history request keys, a reservation request hash, OTP binding fields, consent/recovery fields and history tables. It does not seed or delete permission rows; permission provisioning/grants remain an explicit operator task.

## Implemented in this slice

- `src/repositories/phase08Repository.js` owns an explicit server-side order state graph. A legal transition locks the order row, performs the inventory side effect (where applicable), updates status, writes `order_status_history`, and records audit in one MySQL transaction. Request keys are unique and duplicate-sensitive. Illegal/terminal edges fail closed.
- An inventory reservation foundation uses `stock_reservations` and warehouse/vendor-specific counters; it checks availability, validates rows before release, releases holds on cancellation/failure, and consumes held stock on shipment. It intentionally supports at most one reservation row per product/order because the legacy unique key is `(reservation_key, product_id)`; multiple variant lines for one product are rejected instead of silently corrupting the reservation model. Vendor variants are not supported by the current model. **This foundation is not wired into storefront order creation**; do not claim checkout stock is currently reserved.
- Refund requests are serialized on the parent order and limited by recorded `paid_paisa` less legacy/new pending, approved, processing and completed requests. Requests are idempotent; admin decisions can approve/reject with reasons/history/audit and replays are guarded. No provider settlement/success function is exposed, and no live money is moved. The provider reference column is storage only.
- Admin routes and Bangla/English views exist at `/admin/phase08/orders`, `/admin/phase08/refunds`, `/admin/phase08/incomplete`, and `/admin/phase08/settings`. Mutations use the existing Admin session, permission middleware and CSRF middleware. They require permission names `orders.manage`, `refunds.review`, `checkout.recovery.view`, `checkout.recovery.manage`, and `settings.manage` (or the existing SuperAdmin bypass); migration 0006 deliberately does not overwrite or remove an operator's permission catalogue. Provision/grant these keys through the approved staff-permission process before enabling non-SuperAdmin access.
- Incomplete-checkout capture writes nothing without explicit consent. Captured fields are bounded to normalized phone/name, an opaque session hash, product/variant IDs and quantities; client prices are discarded, and a separate notification-consent flag defaults off. Dedupe is backed by a unique key; replay is safe under concurrent inserts. Admin search/status lifecycle is present. Withdrawal erases contact/session/cart data and prevents silent reactivation. A record can be marked recovered only when the linked MySQL order uses `incomplete:<record-id>` and the same phone. **No checkout order-creation route currently consumes this contract**, so production duplicate prevention is not end-to-end yet. Do not infer anonymous identity or start outreach.
- OTP rows store a keyed digest, expiry, maximum attempts, and binding to exactly one order/customer/session. Verification locks the OTP row, increments failed attempts atomically, rejects expired/verified/replayed/wrong-binding codes, and updates order status only on successful verification. Per-phone hourly issue and per-binding cooldown counters are database-backed. The internal creation result carries the code only for a future delivery adapter; it is never logged and no route sends it. SMS remains `BLOCKED` until approved provider credentials, adapter, and delivery evidence exist.
- Advance configuration validates fixed/percentage mode and bounds and computes integer-paisa advance/COD remainder using `BigInt` for percentage arithmetic. Admin setting persistence/UI exists, but it is **not** connected to authoritative checkout/order writes; no client-submitted price or payment confirmation is trusted.
